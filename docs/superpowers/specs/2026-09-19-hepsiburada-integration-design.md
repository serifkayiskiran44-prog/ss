# Hepsiburada integration design

## Purpose

Add Hepsiburada as a fully operational, account-scoped marketplace inside the existing MonoBridge process. The user must be able to connect one or more Hepsiburada shops, bind selected central catalog products to a chosen shop, match or publish products, manage listing price/stock/dispatch time, inspect Buybox competition, and collect orders into the shared order and inventory flow.

This extends the existing multi-store product architecture. It does not create a second application or a separate Hepsiburada catalog.

## Confirmed user workflow

1. Add a Hepsiburada shop from **Marketplace accounts** using Merchant ID and service key.
2. MonoBridge stores credentials in the connection-scoped Windows DPAPI vault and runs a read-only identity/product-list test.
3. The account becomes operational only after the returned merchant identity and configured Merchant ID agree.
4. In central **Product management**, select products and choose **Connect to shop > Hepsiburada > [shop]**.
5. Refresh that exact shop and match in this order: exact barcode, exact Merchant SKU, explicit manual choice. Duplicate or conflicting matches never bind automatically.
6. A missing remote product becomes a new-product candidate. The user can either select an existing Hepsiburada catalog product or prepare a new catalog submission.
7. Category, mandatory attributes, brand, images, listing price, stock, dispatch time and cargo choices are reviewed before submission.
8. The shop workspace shows connected, unmatched, awaiting-action, rejected, approved and unmanaged products. Double-clicking a row opens the central product card.
9. Price, stock, dispatch-time, content and sale-state writes use immutable previews and explicit approval. A successful receipt updates only that shop binding.
10. Buybox ranking and competitor price are visible per listing. Any automatic price proposal obeys a configured minimum price and still requires approval in the first release.
11. Hepsiburada orders appear in the shared Orders screen with channel and shop identity and reduce the shared online stock once.

## Official API authority

The implementation authority is the official Hepsiburada Developer Portal, reviewed on 2026-09-19:

- Portal and product families: https://developers.hepsiburada.com/tr/companies/hepsiburada
- Service-key setup: `product=api-authentication`, guide `entegratore-servis-anahtari-eklemegoruntuleme`
- Merchant product read: `category=katalog-urun-entegrasyonu`, operation `getAllProductsByMerchantId`
- Listing, stock, price and Buybox: `category=listeleme`, including operation `Buybox Sıralama Sorgulama`
- Orders: the `Sipariş Yönetimi` / `Sipariş Entegrasyonu` product family

The user's Entegra pages are workflow references for connection, product listing, existing-product matching, catalog publication and competition analysis. They do not override the official API contract.

The portal currently documents HTTP Basic Auth, a required Merchant ID and User-Agent, SIT hosts containing `-sit`, and production hosts formed by removing `-sit`. The connection model treats Merchant ID as the Basic Auth user and service key as the Basic Auth password, then verifies that assumption with a harmless merchant-scoped GET before marking the account connected. Credentials are never submitted to an Entegra page.

## Architecture

### Account and credential model

`MarketplaceConnectionStore` continues to hold only non-secret metadata: connection ID, channel, Merchant ID as Shop ID, display name, enabled state, health status and revision.

`MarketplaceCredentialVault` gains the exact `HepsiburadaCredentials` type:

- Merchant ID;
- service key;
- User-Agent generated by MonoBridge, with an optional bounded override for support cases;
- environment (`Production` by default, `Sit` only when explicitly selected).

The legacy global `HepsiburadaSettingsStore` remains readable only for a one-time verified migration. New saves use the per-connection vault. Plain secrets never appear in SQLite, logs, tests, screenshots, exception text, source control or package manifests.

### API client boundary

Create a dedicated `HepsiburadaApiClient` with narrowly typed operations instead of HTTP calls from panels:

- test merchant-scoped read access;
- read all merchant products with pagination;
- read listing records;
- read active categories, category attributes and enum values;
- query product/submission status and tracking history;
- submit or update catalog content;
- approve or reject matching status where supported;
- create/update listings and update price, stock and dispatch time;
- query Buybox ranking and commission data;
- read orders and package state.

Every request uses Basic Auth, the configured Merchant ID, a valid User-Agent, bounded timeouts, disabled automatic redirects and response-size limits. Redirects never forward Authorization. Pagination has explicit page/size bounds and cancellation. `429` handling respects rate-limit headers or a bounded retry delay with jitter. Non-idempotent writes are never blindly retried.

Documented SIT URLs are used only in SIT mode. Production URLs are derived from the official documented host rule and centralized in one environment map so an endpoint cannot accidentally mix environments.

### Workspace and services

Add a specialized `HepsiburadaWorkspacePanel` under the existing `MarketplaceWorkspaceHost`. It reuses common account header, product binding, settings, operation history, product-card event and unified order infrastructure.

Channel-specific responsibilities are divided into focused services:

- metadata service: categories, attributes, brands and allowed values;
- product service: merchant products, status and catalog submissions;
- listing service: listing identity, stock, price, dispatch time and sale state;
- competition service: Buybox rank, winning price, price difference and protected proposal;
- order reader: converts Hepsiburada orders into `OrderSnapshot` with stable channel/shop/order identity.

Remote snapshots and mapping records are scoped by `ConnectionId`. Data from one Hepsiburada account can never satisfy or mutate another account's binding.

## Product identity, matching and publication

Automatic matching follows the user's intended identity rules:

1. exact non-empty barcode when unique locally and remotely;
2. exact Merchant SKU when unique and the barcode does not contradict it;
3. manual selection with both identities visible.

Hepsiburada SKU is stored as the remote catalog/listing identity. Local stock code is never copied into the barcode field. A blank, duplicate or contradictory barcode is a review conflict, not a fallback match.

Publishing is two-stage:

- **Catalog content** creates or updates the Hepsiburada product definition using an active leaf category and its current mandatory properties.
- **Listing** opens that catalog product for the selected merchant with price, available stock, dispatch time and shipping choices.

Existing catalog publication skips content creation and creates/updates only the merchant listing after explicit catalog selection. Submission tracking IDs and status checks are persisted so uncertain responses cannot create duplicates.

## User interface

The Hepsiburada account screen follows the compact Trendyol account layout already accepted by the user:

- **Hepsiburada control**: account products and remote/local comparison;
- **Settings**: masked connection fields, product rules, order rules and synchronization;
- **Competition analysis**: Buybox position, winning price, our price, difference, protected proposal and last read time;
- **Operation history**: redacted API reads, previews, approvals, results and errors.

Product controls include search, detailed filters, multi-selection, product card, refresh, match, catalog selection, category/attribute mapping, listing preview, price preview, stock preview, dispatch-time preview and deactivate preview. Buttons appear only when the selected account advertises and implements the capability.

The connection form stays simple: Merchant ID, service key, environment and optional User-Agent override. The saved service key is never displayed again; the field shows only that a secret is stored and supports deliberate replacement.

## Competition analysis

Buybox data is read-only by default. Each row shows Hepsiburada SKU, Merchant SKU, our listing price, winning price, rank/order and last refresh. A pricing rule may calculate a proposed price using minimum price, maximum decrease and rounding rules.

The proposal cannot undercut the protected minimum, bypass catalog price locks or mutate a listing. First-release application always creates a normal immutable price preview and requires explicit approval. Scheduling only refreshes Buybox data; it does not write prices.

## Orders and inventory

The account-scoped adapter declares `OrdersRead` and maps Hepsiburada order/package data into the existing unified order store. The stable idempotency key is `(hepsiburada, ConnectionId, remote order or line identity)`.

A newly imported paid order reduces the shared online location once. Re-reading the order is idempotent. Cancellation and return use the existing explicit stock-restoration decision flow. Package, cargo, invoice, desi and shipment-state writes are deferred until their individual API contracts and user workflows are implemented; read fields may still be displayed when returned by order APIs.

## Safety and failure behavior

- Connection validation is read-only and cannot publish or modify a listing.
- All remote writes require an immutable preview, current connection revision, current product/binding revision, exact shop identity and explicit approval.
- Content, price, stock and dispatch-time management switches are independent. Disabled management preserves the remote value.
- Successful results persist durable receipts before the UI reports success.
- Ambiguous, malformed or oversized API responses fail closed with a redacted actionable message.
- `401`/`403` marks credentials as needing attention without deleting them; `429` schedules a bounded retry; validation errors attach to the affected row; one row failure does not apply other unapproved rows.
- Background reads run through the existing single-process scheduler and never display modal dialogs.
- Live writes are not performed by automated tests or by initial connection setup.

## Capability registration

After the real implementations are present and tested, the Hepsiburada definition enables:

- `ProductsRead`
- `OrdersRead`
- `ProductManagement`
- `ContentWrite`
- `CategoryWrite`
- `PropertiesWrite`
- `ListingCreate`
- `PriceWrite`
- `StockWrite`
- `DeliveryWrite` for dispatch-time management

No capability is advertised while its command still throws a placeholder or lacks a tested API contract.

## Testing and verification

All contract tests use temporary data and fake HTTP handlers. Required coverage includes:

- credential validation, DPAPI vault type/identity isolation and secret redaction;
- SIT/production host separation, Basic Auth and required User-Agent;
- redirect credential stripping, timeout, response bounds and cancellation;
- pagination, malformed data and rate-limit handling;
- exact barcode/Merchant SKU matching, duplicates and conflicts;
- category and mandatory-attribute validation;
- catalog/listing preview revision fences and duplicate-submission protection;
- price/stock/dispatch-only payload isolation;
- Buybox minimum-price protection;
- multi-account isolation;
- order idempotency and stock reduction;
- account navigation, capability-gated buttons and product-card opening.

Verification requires the exact Release test suite, self-contained `win-x64` publish, package smoke test, visible application launch and a read-only connection test against the supplied account. No live product write is used as a connection test.

## Acceptance criteria

- The supplied Hepsiburada account can be saved in the encrypted account vault and pass a merchant-scoped read-only test.
- A second Hepsiburada account can be added without sharing credentials, mappings, products or receipts.
- The user can select central products and bind them to a chosen Hepsiburada shop.
- Existing merchant products can be refreshed and matched without putting SKU into barcode.
- Missing products can be prepared either from an existing Hepsiburada catalog record or as a reviewed new catalog submission.
- Price, stock and dispatch time can be previewed and applied independently.
- Buybox rank and price comparison are visible without changing price automatically.
- Orders enter the shared order list and reduce shared online stock at most once.
- Existing Trendyol, Etsy, XML, physical-store and manual product flows continue to pass regression tests.

## Deferred scope

Automated live repricing, campaign creation, package-state mutation, cargo-label generation, invoice upload, accounting settlement and return/claim mutation are outside the first Hepsiburada release. Their read models may be retained for later work, but no UI control advertises an unimplemented write capability.
